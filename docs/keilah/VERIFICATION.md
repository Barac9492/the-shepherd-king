# DB 연결 구현 검증 결과

운영에 연결할 수 있는 Vercel API + Supabase RPC/migration을 구현했으며, 모든 쓰기 검증은 로컬에서 수행했다. 메모리 서버만을 최종 구현으로 사용하지 않는다.

## 최종 결과

| 검증 | 결과 |
| --- | --- |
| 핵심/전체 스토리/랭킹/신규 서버 종합 | 332/332 |
| 그중 신규 PostgreSQL/RPC/HTTP | 11/11 |
| 독립 320px·390px 협동 브라우저 | 8/8 |
| 응답 유실·순서 뒤바뀜·복구 브라우저 | 4/4 |
| 실제 서버 프로세스 종료/재시작 | 완주 기록 동일 |
| 보안 catalog preflight | RLS·invoker·anon/authenticated 거부·인덱스 확인 |

모든 최종 실행 exit 0. 종합 332개는 기존 핵심/스토리/랭킹 311개 + 메모리 모델 10개 + 신규 DB 11개다. 앞서 같은 메뉴 변경에서 통과한 메뉴 15, 댄스 15, 엔게디 13, 물맷돌 14, 산책 15, 정원 19개도 유지했다. 새 라우트는 기존 게임 API 경로와 분리되어 있으며, 종합 검증에서 기존 DB/API 검산 테스트를 다시 실행했다.

## 실제 DB 협동 완주

운영용 HTTP 핸들러 → Supabase 서비스 어댑터 → 동일 migration/RPC를 로컬 파일 PostgreSQL에서 실행했다. 요청마다 새 핸들러/서비스를 만들어 메모리 방을 공유하지 않았다.

두 독립 모바일 컨텍스트의 실제 완주 **218,739ms (3분 38.7초)**. 시간을 가속하거나 완주 상태/기록을 직접 넣지 않았다. 양쪽 동시 구출, 한 가족씩 남문 인솔, 네 가족 도착, 두 사람의 탈출, 공개 동의와 영속 TOP 10을 확인했다. 실제 서버 프로세스를 종료·재시작하고 공개 기록 JSON이 동일함을 확인했다.

브라우저 8개 흐름: 1280/390/320 화면, 중복 생성·두 자리 제한, 준비/취소·키보드, 실제 협동 완주, 내부 순위·재도전, 연결 끊김/복구와 새로고침, 나가기/재입장/메뉴 복귀 후 폴링 정리, 오프라인 나가기. pageerror 없음.

추가 4개 흐름: 서버가 입장을 처리한 뒤 응답을 잃고 새로고침해도 같은 자리를 복구, 동의 없는 준비 거부, 준비 응답 유실 후 중복 토글 없음, 과거 응답이 최신 revision을 덮어쓰지 않음, 준비/동의 상태 새로고침 복구와 탈퇴 정리.

## SQL·권한·공정성

- 실제 지도 데이터와 SQL 고정 지도 일치
- 동시에 들어온 두 입장 중 한 명만 두 번째 자리를 확보
- 자리 capability/다른 방 격리, anon/authenticated 직접 접근 및 RPC 거부
- 같은 명령 재전송은 한 번만 처리, 다른 명령의 sequence 재사용 및 이전 run 거부
- 클라이언트 시간·점수·위치 제출, 순간 이동, 조기 탈출, 동의 없는 시작 거부
- 처음 통로 통과에는 동료의 손잡이 필요, 중도 해제는 통과 취소
- 12초 grace, 이후 공유 진행 정지, 60초 이내 복구와 실제 시간 누적, 초과 시 종료
- 완료 후 동료가 나가도 완료 상태/기록 보존
- 같은 DB에 기존 댄스·엔게디 migration 및 보존용 물맷돌 probe를 둔 채 새 migration을 적용해 기존 행/RPC 보존 확인
- DB 파일을 닫고 다시 열어 방/토큰 접근 유지 확인
- 공개 순위는 초대 코드 대신 별도 팀 ID 사용

단위 테스트의 긴 이동은 격리 DB에만 주입한 결정적 시계로 검증했다. 실제 브라우저와 파일 DB 재시작 검증에는 원본 migration과 실제 DB 시간을 사용했다.

## 미검증과 승인 범위

실제 Android/iOS, 이동통신/Wi-Fi 전환, 배포된 Vercel rewrite와 실제 Supabase 왕복, 운영 PostgreSQL 다중 연결 부하/인터넷 지연은 미검증이다. 로컬 Docker daemon이 실행되지 않아 별도 PostgreSQL 서버 부하 시험 대신 PGlite 엔진에서 원자적 RPC·동시 HTTP 요청을 검증했다. 실제 두 사람인지 또는 자동화인지를 완전히 판별하지 않는다.

원격에서는 프로젝트 메타데이터와 migration 목록만 읽었다. 새 migration 적용, 환경 변경, 운영 방/점수/DB 쓰기, push/PR/병합/배포는 하지 않았다. 공식 운영 advisors는 아직 적용하지 않은 새 스키마를 검사할 수 없으므로 승인 후 적용 절차에 포함했다. 로컬에서는 같은 보안 catalog를 직접 검사했다.
